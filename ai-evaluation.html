Case study · AI Evaluation

Making AI output reliable enough to ship.

The other half of the same discipline: where Arzìqi is about trusting financial data, this work was about trusting what a large language model produces — evaluating AI-generated code for correctness and production-readiness.

Role · AI Model Evaluator (LLMs) Anthropic — via Turing Remote

The work

Evaluate AI-generated Rust code for correctness, completeness, and production-readiness inside large language models.

The lens

Not "does it look right" — "would a developer actually ship this?" Judgment under ambiguity, at the boundary of what the model gets right.

The method

Comparative analysis of model outputs, structured qualitative + quantitative feedback, evaluation metadata in Git-based workflows.

The outcome

Feedback that improved model reliability and lifted developer usability — turning evaluation signal into iterative model improvement.

Why this matters

A model that sounds confident but can't be trusted does real damage — the same failure Arzìqi exists to prevent, in a different domain.

AI-generated code is the sharp end of the trust problem: it's fluent, plausible, and often subtly wrong. My job was to be the human who tells the difference — rigorously, repeatably, and in a way that feeds back into a better model. That's product-adjacent evaluation work: defining what "good" means, then judging against it consistently enough that the signal is useful.

What I hunted for

Failure mode

Hallucinations

Confident, fluent output that invents APIs, behavior, or facts that don't exist — the most dangerous because it's the most convincing.

Failure mode

Instruction-following gaps

Output that drifts from the actual task — solving a nearby problem, ignoring a constraint, or quietly changing the spec.

Failure mode

Reasoning errors

Logic that breaks under scrutiny — right-looking steps that don't actually compose into a correct result.

Failure mode

Incompleteness & production-readiness

Code that "works" in the happy path but isn't correct, complete, or usable enough for a developer to actually ship.

How it connects to my product work

Both sides of my work answer the same question — can you trust what this system is telling you? In Arzìqi, I make fragmented financial data trustworthy enough to act on. In model evaluation, I make AI output reliable enough to ship. Both require defining "trustworthy" precisely, judging against it consistently, and caring most about the failures that hide behind a confident surface. That instinct — for the gap between looks right and is right — is the throughline of how I build and assess products.

Two domains, one instinct.

Happy to talk through evaluation frameworks, fintech product, or where AI and trust meet.
